Interview Q&A

Technical questions tailored for the NVIDIA IPP Senior Software Engineer role — covering RAG, fine-tuning, system design, and Kubernetes

Architecture & System Design

I separated network I/O from AI compute based on objective performance requirements.

Go for the Network Layer: The API Gateway needed to handle high-throughput webhook traffic from GitHub/CI systems. Go with Gin achieved 40,000 RPS with 30MB memory — that's 5× throughput and 6× memory efficiency vs an equivalent Python (FastAPI) implementation. For a service that's essentially proxying and rate-limiting, Go's goroutine model is ideal.

Python for AI: There's no viable alternative. LangChain, LangGraph, Sentence Transformers, PEFT, vLLM — the entire ML/AI ecosystem is Python-first. Fighting that ecosystem would cost more than the polyglot overhead.

Integration: Standard microservice patterns (HTTP + Redis Streams + OpenTelemetry) made the language boundary transparent. The 30-40 hour overhead of maintaining two languages paid for itself in the 4× Gateway performance gain — critical when running 13 pods on 2 small nodes.

Two patterns depending on the use case:

Synchronous (HTTP): API Gateway proxies requests to backend services (agent-orchestrator, metrics, indexing) via HTTP. Simple, debuggable, with built-in retry logic. Used for all user-facing request-response flows.

Asynchronous (Redis Streams): The Ingestion Service publishes webhook events to Redis Streams. The Agent Orchestrator consumes events asynchronously. This decouples ingestion throughput from AI processing latency — critical because LLM inference takes 1-3 seconds vs the 5ms webhook acknowledgment SLA.

Why not Kafka/RabbitMQ? Redis Streams provides exactly-once semantics with consumer groups, and we already had Redis for rate limiting and caching. Adding another message broker would increase operational complexity for a system that processes hundreds, not millions, of events per minute.

Horizontal scaling (immediate): HPA is already configured for all services. The Go Gateway scales linearly — add replicas. Python services scale with gunicorn workers per pod plus more pods.

Inference bottleneck: At 100x, LLM inference becomes the bottleneck. I'd move from single OpenRouter calls to batched inference with vLLM on GPU nodes (g5.xlarge). vLLM's continuous batching can serve 50-100 concurrent requests on a single A10G.

Data layer: PostgreSQL would need read replicas for the metrics service. Elasticsearch already shards well. Redis would need cluster mode for the cache layer.

Architecture changes: I'd add a request queue (SQS/Kafka) in front of the agent orchestrator to absorb traffic spikes, and implement circuit breakers (already have Redis-based rate limiting as a foundation).

Trade-offs made:

  • OpenRouter vs local inference: Production uses OpenRouter API proxy because t3.large nodes lack GPU. This adds ~500ms network latency but eliminates the $0.50/hr per GPU node cost. For a portfolio project, this was the right call.
  • Kustomize vs Helm: Used Kustomize for application manifests (simpler, less templating complexity) and Helm only for third-party tools (ArgoCD, ALB Controller, Prometheus). Some teams prefer all-Helm; I value readability for interview discussions.
  • No service mesh: Istio/Linkerd would add mTLS and observability but also 200MB+ sidecar overhead per pod. With 13 pods on 16GB, that's not viable. OpenTelemetry manual instrumentation was sufficient.

What I'd change:

  • Add proper end-to-end integration tests that actually call the live cluster
  • Implement proper secret management (AWS Secrets Manager + External Secrets Operator) instead of K8s Secrets
  • Add Grafana dashboards with pre-configured alerts for DORA metrics

RAG & AI Architecture

The RAG pipeline has three stages:

1. Indexing (offline): Build failure logs are embedded using all-MiniLM-L6-v2 (384-dim vectors) and stored in both Faiss (vector index) and Elasticsearch (full-text BM25 index). This dual-index approach enables hybrid search.

2. Retrieval (online): When a new failure arrives, I run parallel queries — BM25 keyword search on Elasticsearch and cosine similarity search on Faiss. Results are merged using reciprocal rank fusion (RRF), then reranked for relevance. This hybrid approach catches failures that share technical terms (BM25) AND semantic meaning (vector) — catching cases each method alone would miss.

3. Generation: The top-k retrieved documents (similar past failures + their resolutions) are concatenated with the new failure log and sent to the LLM. The prompt is structured to generate: root cause, severity classification, fix steps, and confidence score.

Why hybrid over pure vector search? In DevOps logs, exact error codes and package names matter. Vector search alone might miss "ECONNREFUSED" matching "connection refused" at the keyword level. BM25 catches exact matches; vectors catch semantic similarity. Combined, they achieve higher recall.

Model: Qwen2.5-7B as the base model — strong multilingual capability, good reasoning for code analysis.

Method: LoRA (Low-Rank Adaptation) via PEFT library. Rank-16 adapters on attention layers only. This reduces trainable parameters from 7B to ~4M (0.06%) while preserving the base model's general capabilities.

Task: Fine-tuned a classifier for build failure categorization — infrastructure, dependency, test, configuration, code. This runs before RAG retrieval to route failures to the most relevant index partition.

Training: 500 labeled examples of CI failures, augmented with GPT-4 generated variations. 3 epochs, learning rate 2e-4, batch size 4 with gradient accumulation. Training takes ~30min on a single A10G GPU.

Why LoRA over full fine-tuning? Memory efficiency (fits on a single 24GB GPU), faster training (30 min vs 8+ hours), and the adapter is only 16MB — easy to version, deploy, and swap for different classification tasks.

The problem: LangChain's basic chain/agent paradigm is linear. Real incident response requires multiple specialized agents collaborating with conditional logic — if severity is P1, escalate immediately; if diagnosis is uncertain, loop back for more evidence.

LangGraph solution: It provides a state machine / directed graph for agent orchestration. Each node is a specialized agent (triage, diagnosis, resolution, communication). Edges have conditions. State is passed between nodes and persisted.

Concrete example — Incident Response:

  1. Triage Agent classifies severity → if P1, parallel-execute Diagnosis + Communication
  2. Diagnosis Agent analyzes logs → if low confidence, loop back with additional data
  3. Resolution Agent generates runbook → depends on Diagnosis output
  4. Communication Agent drafts updates → incorporates all prior agent outputs

Key advantage: LangGraph gives me control flow (conditionals, loops, parallel execution) that basic chains can't express. The incident workflow has a state schema with typed fields, making it debuggable and testable — unlike opaque chain outputs.

Retrieval metrics:

  • Recall@k: What percentage of relevant documents appear in the top-k results. Target: >0.85 at k=5.
  • MRR (Mean Reciprocal Rank): How high the first relevant result appears. Target: >0.7.

Generation metrics:

  • Faithfulness: Does the answer only use information from retrieved docs? Manual spot-checking + automated LLM-as-judge evaluation.
  • Relevance: Does the answer address the actual failure? Measured by comparing generated root cause against known resolutions in our test set.

End-to-end: Confidence score from the model itself (calibrated against test set). Tracked via DORA metrics — MTTR reduction is the ultimate evaluation: 45 min manual → 8 min AI-assisted = 5.6× improvement.

Kubernetes & DevOps

CI (GitHub Actions):

  • Triggered on push to main and PRs
  • Matrix strategy: Go ×2 services (test + lint), Python ×4 services (test + lint), Frontend (test + build)
  • Each service tested independently — failure in one doesn't block others
  • Total: 470 tests, ~3-4 min wall clock

CD (GitHub Actions → ArgoCD):

  1. On CI success, CD workflow triggers
  2. OIDC authentication to AWS (no stored credentials)
  3. Docker build + push to ECR with sha-<commit> tag (no :latest)
  4. Updates k8s/overlays/production/kustomization.yaml with new image tags
  5. Commits kustomization change back to main
  6. ArgoCD detects git change, auto-syncs cluster

Why this approach? ArgoCD as the single source of truth for cluster state. No kubectl apply in CI — all changes go through Git. Rollback = revert the kustomization commit.

Current approach: Kubernetes Secret objects with base64-encoded values, deployed via kubectl create secret. ArgoCD is configured with ignoreDifferences on secret data to prevent selfHeal from overwriting manually-set secrets.

Challenges encountered: ArgoCD's selfHeal kept reverting secrets to the Git-stored (empty/placeholder) values. Solved with:

ignoreDifferences:
- group: ""
  kind: Secret
  jsonPointers:
  - /data

Plus RespectIgnoreDifferences=true sync option.

Production improvement: In a real environment, I'd use AWS Secrets Manager + External Secrets Operator to sync secrets from AWS into K8s Secret objects automatically. This eliminates manual secret management and provides audit trails.

Decision criteria:

  • Readability: Kustomize uses plain YAML with overlays. During an interview, I can show the exact K8s manifest that runs in production — no template rendering step.
  • Simplicity: 8 services with similar deployment patterns. Kustomize's strategic merge patches are sufficient. Helm's templating power (conditionals, loops, helpers) isn't needed.
  • ArgoCD native: ArgoCD has first-class Kustomize support. No Helm release management overhead.

Helm for third-party: I use Helm for ALB Controller, ArgoCD, and kube-prometheus-stack because these charts manage complex CRD installations and version upgrades that would be painful to maintain as raw YAML.

Structure: k8s/base/ (8 deployments, services, configmaps) + k8s/overlays/production/ (resource patches, HPA, ingress). Clean separation of concerns.

selfHeal: ArgoCD continuously compares the live cluster state against the Git-declared desired state. If someone manually changes a resource (kubectl edit, kubectl scale), selfHeal automatically reverts it within seconds. This enforces GitOps — Git is the single source of truth.

Issue encountered: selfHeal was overwriting the Secret's data field. The Kubernetes Secret had been manually patched with the real API keys/passwords (not stored in Git for security). Every selfHeal cycle would reset these to the placeholder values from Git.

Solution: Three-part fix:

  1. ignoreDifferences on Secret data in the ArgoCD Application spec
  2. RespectIgnoreDifferences=true in syncOptions (makes selfHeal honor the ignore rules)
  3. Documented that secrets must be applied manually after initial deploy

Lesson: GitOps purists would say "everything in Git, use sealed-secrets or external-secrets." Pragmatically, for a portfolio project with a single cluster, the ignoreDifferences approach is simpler and sufficient.

Performance & Optimization

Four key factors:

  1. Go + goroutines: Each request gets its own goroutine. No thread pool exhaustion, no GIL. The Go runtime schedules goroutines across OS threads efficiently.
  2. Connection pooling: Both Redis and HTTP backend connections are pooled. The Redis pool maintains 100 persistent connections; HTTP clients reuse TCP connections with keep-alive. This eliminates the TCP handshake + TLS overhead per request.
  3. Response caching: Redis-backed cache middleware with configurable TTL. For repeated health checks and read-heavy endpoints, cache hit rate is ~90%. Cache miss falls through to the backend service.
  4. Minimal allocation: Gin framework is designed for zero-allocation routing. We pre-allocate response buffers and reuse JSON encoders. The 30MB memory footprint means the garbage collector rarely pauses.

Measurement: wrk -t4 -c100 -d30s http://localhost:8000/health consistently produces 40k+ RPS on a 4-core machine.

Test suite as safety net: All 470 tests ran before and after every optimization. Zero test failures post-optimization (Week 10).

Incremental approach: Each optimization was applied and tested independently — connection pooling first, then caching, then gunicorn workers. Never multiple changes at once.

Behavioral verification: Integration tests verify that API contracts haven't changed. A cached response must be identical to an uncached response (verified by test).

Resource monitoring: Docker Compose resource limits prevent any service from starving others. The metrics service caches were tested for memory growth over 24-hour simulated loads.

NVIDIA IPP-Specific

NVIDIA's IPP (Intelligent Pipeline Platform) orchestrates AI/ML workflows at scale. My project directly mirrors these challenges:

  • Multi-agent orchestration: LangGraph workflows are analogous to NVIDIA's pipeline DAGs — coordinating multiple AI models with conditional logic and state management
  • Model serving: The model-service with vLLM/OpenRouter reflects NVIDIA's Triton Inference Server patterns — model loading, batching, GPU memory management
  • Scale concerns: Running 8 AI services on constrained hardware (2× t3.large) required the same resource optimization thinking that GPU cluster management demands
  • RAG pipelines: NVIDIA's NeMo Retriever and my Elasticsearch + Faiss hybrid search solve the same retrieval problem at different scales

Key differentiator: This isn't a tutorial project. It runs in production on AWS, handles real webhook events, and has been optimized across every layer. I've made engineering trade-offs (not toy decisions) and can discuss them in depth.

ArgoCD selfHeal + secrets management on EKS.

The system was live with 13 pods, but ArgoCD kept reverting the OpenRouter API key secret every 3 minutes. The model-service would crash, agent-orchestrator would timeout, and the entire AI pipeline would go down.

Debugging process:

  1. Identified the issue via kubectl logs on argocd-application-controller
  2. Realized selfHeal was comparing Git (placeholder) vs live (real key) and "healing" back to placeholder
  3. First fix: ignoreDifferences — didn't work because selfHeal ignores ignoreDifferences by default
  4. Second fix: Added RespectIgnoreDifferences=true syncOption — this was the key insight
  5. Also had to increase model-service resources (100m→1000m CPU) because torch startup was getting OOMKilled

Why it was hard: Multiple failure modes overlapping — secret overwrite + resource starvation + probe timeouts all looked like "model-service crashing." Had to isolate each issue independently while the cluster was live.

Through DORA metrics — the industry-standard framework for measuring DevOps performance:

  • MTTR reduction: 45 min (manual triage) → 8 min (AI-assisted) = 5.6× improvement. This is the primary ROI metric.
  • Deployment frequency: With automated PR risk assessment and code review, teams can merge faster with confidence. Tracks from weekly to daily deployment cadence.
  • Change failure rate: AI-assisted code review catches issues before merge. Measuring the percentage of deployments that cause production incidents.
  • Lead time: From commit to production deployment. The CI/CD pipeline (3-4 min CI + 2 min CD + instant ArgoCD sync) provides baseline data.

Concrete example: If an engineering team of 20 spends an average of 45 min per build failure, and they have 3 failures per day, that's 45 hours/week of engineer time. At 5.6× improvement, AI triage recovers ~37 hours/week — nearly a full engineer's capacity.
