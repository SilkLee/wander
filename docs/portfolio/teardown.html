Teardown Guide

Step-by-step instructions to safely decommission the WorkflowAI production environment on AWS EKS

⚠ Destructive Operations Ahead

This guide permanently deletes all AWS resources created by Terraform and Kubernetes. Ensure you have exported any data, logs, or configurations you want to preserve before proceeding. All commands should be run from the repository root (workflow-ai/).

Step 1 — Delete Application Workloads

Remove all 13 pods, services, ingress rules, PVCs, and ConfigMaps in the workflowai namespace.

1a. Verify current state

# List all resources in the namespace
kubectl get all -n workflowai
kubectl get pvc -n workflowai
kubectl get ingress -n workflowai
kubectl get configmap -n workflowai
kubectl get secret -n workflowai

1b. Delete the namespace

# This cascades — deletes ALL resources within the namespace
kubectl delete namespace workflowai --ignore-not-found

# Wait for namespace termination (may take 1-2 minutes for PVC/ALB cleanup)
kubectl wait --for=delete namespace/workflowai --timeout=120s 2>/dev/null || true

Note: If namespace gets stuck in Terminating state, it's usually because a finalizer is waiting for the ALB to be deprovisioned. Wait 2-3 minutes for the ALB Controller to clean up the load balancer, then the namespace will terminate.

Step 2 — Remove ArgoCD Root Application

Delete the ArgoCD app-of-apps to prevent it from recreating the workflowai namespace after deletion.

# Delete the root application and project
kubectl delete -f k8s/argocd/root-app.yaml --ignore-not-found
kubectl delete -f k8s/argocd/projects/workflowai-project.yaml --ignore-not-found

# Verify no ArgoCD apps remain for workflowai
kubectl get applications -n argocd 2>/dev/null || echo "ArgoCD namespace already gone"

Why this matters: ArgoCD's selfHeal: true setting means it will automatically recreate any resources you delete if the root app is still present. Always remove the ArgoCD app before or immediately after deleting the namespace.

Step 3 — Uninstall Cluster Tooling

Remove Helm-managed cluster-level components installed by the bootstrap script.

3a. Uninstall kube-prometheus-stack

helm uninstall prometheus -n monitoring 2>/dev/null || true
kubectl delete namespace monitoring --ignore-not-found

3b. Uninstall ArgoCD

helm uninstall argocd -n argocd 2>/dev/null || true
kubectl delete namespace argocd --ignore-not-found

3c. Uninstall AWS Load Balancer Controller

helm uninstall aws-load-balancer-controller -n kube-system 2>/dev/null || true

Important: The ALB Controller must be uninstalled before destroying the EKS cluster. If the controller is still running when the cluster is deleted, the AWS ALB it created may become orphaned and require manual deletion in the EC2 > Load Balancers console.

3d. Clean up CRDs (optional)

# Prometheus CRDs
kubectl delete crd alertmanagerconfigs.monitoring.coreos.com \
  alertmanagers.monitoring.coreos.com podmonitors.monitoring.coreos.com \
  probes.monitoring.coreos.com prometheuses.monitoring.coreos.com \
  prometheusrules.monitoring.coreos.com servicemonitors.monitoring.coreos.com \
  thanosrulers.monitoring.coreos.com 2>/dev/null || true

# ArgoCD CRDs
kubectl delete crd applications.argoproj.io applicationsets.argoproj.io \
  appprojects.argoproj.io 2>/dev/null || true

Step 4 — Destroy Terraform Infrastructure

This is the most impactful step — it deletes the VPC, EKS cluster, ECR repositories, IAM roles, and all associated AWS resources.

4a. Review what will be destroyed

cd infra/terraform
terraform plan -destroy

Review the output carefully. You should see ~40-50 resources marked for destruction.

4b. Execute destruction

# Destroy all Terraform-managed resources (~10-15 minutes)
cd infra/terraform
terraform destroy -auto-approve

# Or use the Makefile shortcut:
make terraform-destroy

Common failure: ENI stuck in use

If terraform destroy hangs on VPC/subnet deletion, it's usually because an Elastic Network Interface (ENI) is still attached to a deleted load balancer. Wait 5 minutes for AWS to release it, then re-run terraform destroy -auto-approve. If it persists, manually detach and delete the ENI in the EC2 > Network Interfaces console.

Step 5 — Remove Terraform State Backend (Optional)

The Terraform state backend (S3 + DynamoDB) was created by a separate bootstrap Terraform config. Delete it only if you're fully done with the project.

# Empty the S3 bucket first (required before deletion)
aws s3 rm s3://workflowai-terraform-state --recursive

# Destroy the bootstrap resources
cd infra/terraform/bootstrap
terraform destroy -auto-approve

This removes the workflowai-terraform-state S3 bucket and workflowai-terraform-locks DynamoDB table in ap-southeast-1.

Step 6 — Verification Checklist

Confirm all resources have been successfully deleted to avoid unexpected AWS charges.

CLI Verification

# EKS cluster should be gone
aws eks list-clusters --region ap-southeast-1
# Expected: { "clusters": [] }

# ECR repositories should be gone
aws ecr describe-repositories --region ap-southeast-1 2>/dev/null || echo "No ECR repos"
# Expected: error or empty list

# VPC should be gone (check for workflowai VPC)
aws ec2 describe-vpcs --region ap-southeast-1 \
  --filters "Name=tag:Name,Values=*workflowai*"
# Expected: { "Vpcs": [] }

# No orphaned load balancers
aws elbv2 describe-load-balancers --region ap-southeast-1
# Expected: No load balancers with "workflowai" in the name

# No orphaned EBS volumes
aws ec2 describe-volumes --region ap-southeast-1 \
  --filters "Name=tag:kubernetes.io/cluster/workflowai,Values=owned"
# Expected: { "Volumes": [] }

Quick Teardown (One Command)

For a fast teardown that handles steps 1 + 4 in a single command:

# From the repository root:
make clean

This runs kubectl delete namespace workflowai --ignore-not-found followed by terraform destroy -auto-approve. Note: it does not uninstall Helm releases (step 3) or clean up the state backend (step 5). For a complete teardown, follow the full step-by-step guide above.
